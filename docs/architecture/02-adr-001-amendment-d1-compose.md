## 2. Security, integrity and compatibility

- Use non-root TLSBeacon execution with minimal capabilities and mounts; give neither project container Docker socket/API access, privileged mode or host networking. Effective local Docker access is privileged infrastructure authority, not granted by trust as a TLSBeacon operator or by a restricted PostgreSQL role.
- Use private database reachability, explicit runtime authentication and separate administrative/setup credentials confined to the roles and operations that need them. Starting a new PostgreSQL cluster may require database-side bootstrap inputs; this is not initialization of the TLSBeacon schema. Routine CLI invocations receive only runtime credentials. Never weaken database transport security via probe TLS settings.
- Keep local files protected at rest and in use. Exclude `.tlsbeacon-local/` in both `.gitignore` and `.dockerignore`; do not copy into images, interpolate into command arguments, or disclose in output or logs. Pass only the individual necessary files; verify host and in-container permissions for the actual execution identity, including unsafe-path rejection. Neither the whole checkout nor the whole secrets directory is a runtime mount.
- Compose does not authorize probe destinations. ADR-001 §6 applies to every actual numeric address, port and scope, including retries. Resolver traffic to the operator-controlled installed resolver is a prerequisite, not a target grant. Document explicit enumerable Linux root sources; never substitute roots or silently disable an address case.
- Pilot selection is explicit and independent of the checkout and Compose default project name. Bind a protected operator-maintained enrollment record to the intended local Engine, persistent volume, PostgreSQL cluster and installation/database; verify live identity and dependencies before use or mutation. Ordinary startup cannot create a replacement; explicit first bootstrap and transactional schema setup are separate, as specified in the paired contract. No guessing or destructive recovery on ambiguous state.
- The Compose launcher uses a separate short-lived verifier on the private DB bridge to authenticate to the selected live database with a dedicated, identity-read-only login independent of the child and schema setup. It does not gate on application schema readiness or child runtime settings or credentials. The verifier and actual child authenticate every DB connection to the same published generation-specific TCP server key, not just to the same CA/name or copied SQL witness. The launcher passes the pin separately from child inputs. Confirmed absent slots are omitted, safe child-unreadable inputs may be mounted, and unsafe or unrealizable mounts remain infrastructure refusals. After valid selection and safe launch, the actual CLI owns runtime configuration, authentication and storage errors, including missing or incompatible schema. The launcher preserves verified CLI exits and separates infrastructure failure and known interruption; the directly invoked host CLI retains the legacy exit/stream contract without launcher codes. See paired contract §§2.2–2.3 and C-V01.
- Preserve all V-01–V-10 guarantees, including immutable root selection, stable IDs and no-ops, atomic mutations/unknown commits, independent certificate dimensions, actual dial and time-budget evidence, and existing report/exit semantics. Pilot stop and restart retain the volume and configuration; no D1 backup/restore guarantee. Full tested backup and restore remain D3.

### 2.1 Linux network qualification approach

- On Linux Docker Engine, attach the one-off CLI to a private internal DB bridge (the DB's only network) and a separate user-defined dual-stack probe bridge, with the probe bridge supplying intended lab routes. No ports are published. Configure the installed resolver path through the CLI namespace to operator-controlled DNS reachable on that topology (for example, Docker's embedded DNS forwarding to an explicitly selected lab resolver); document and qualify actual upstream, search behavior, IPv4/IPv6 answers, cancellation and absence of unintended fallback. A host-only DNS stub is not reachable as container loopback.
- In a controlled qualification run, attach TLS and DNS peers as needed on the probe bridge for real DNS, IPv4 and IPv6 dials. Put a scoped IPv6 link-local TLS peer on that same L2 link; qualify link-local addresses and neighbor reachability on both bridge attachments used for that dial (CLI and peer). The zone in the registered target and policy is the CLI namespace's probe-facing interface, not the host bridge or the peer interface. Identify that interface deterministically or validate its actual mapping on each disposable invocation before relying on it. Record the socket-visible numeric peer and effective scope; the zone is not part of SAN identity.
- Compose loopback means the one-off CLI namespace's `127.0.0.1` / `::1`, never host loopback. Qualify actual namespace-local TLS listeners using the same CLI image, with equivalent DB/probe attachments and effective resolver/search behavior; a disposable test-only namespace holder is acceptable if equivalence is demonstrated. Ordinary pilot use requires no namespace holder. For host-loopback-only listeners, run the installed CLI in the host namespace. It uses the host resolver and actual host interface scope where applicable. Both paths authorize every numeric dial using the same enrolled policy rules and immutable selected registry context. Reachability is namespace-specific, not a grant; no host networking, privilege expansion, proxy, rewriting, scope substitution, firewall change or rebind of a monitored listener is required.
- C-V03 separates actual host and one-off dials from virtual-denial evidence. Effective IPv6 link-local, DNS search/cancellation, route and permission behavior remain unqualified. Stop affected work if the supported topology cannot meet the contract; do not silently narrow reachability or relax isolation.

### 2.2 Host-run access to the same registry

Propose PostgreSQL's own filesystem Unix-domain listener in a dedicated per-installation directory bind-mounted only into the DB service. This is a local database transport, not a TLSBeacon service/control socket or TCP publication. The DB continues to serve the one-off CLI on the private bridge; the host CLI uses only the selected Unix socket and no Docker API, direct bridge route, TCP fallback or relay. The only new DB reachability is the designated local operator through that filesystem boundary. The DB process may create/remove its socket and lock in a dedicated leaf; it cannot replace the protected parent or access unrelated host paths. Qualify actual host/container UID/GID mappings, directory traversal and socket connect permissions (e.g., a dedicated group limited to the DB service identity and designated operator, without group directory write). No world-accessible socket, shared writable parent or grant of Docker authority. If mappings or repeatable isolation cannot be qualified without broadening access, stop and seek an explicit Level 2 decision; no TCP listener publication or privilege grant is a fallback.

Authenticate the host endpoint through the protected filesystem and verified kernel peer identity of the connected socket, then authenticate to the specific PostgreSQL database/role using an explicit strong password method such as SCRAM. No `trust`, ambient libpq-style override, alternate socket/address, or probe TLS setting is used. Security of this local transport relies on kernel isolation and controlled socket ownership, not TLS over the Unix socket. Container DB TCP has separately qualified server authentication and transport settings. Deployment identity, including pre-schema DB evidence, must agree on both routes; verify it on the connection actually used and on replacement/reconnect before any registry access. Bind the host connection to the enrolled storage through a live postmaster generation, not through a prior readiness check or copied database markers. The authorized lifecycle operator verifies the exact Engine, container, effective data mount and live cluster/database, then publishes a protected, boot-scoped binding to the kernel process object that owns the direct PostgreSQL listener. The installed CLI verifies that object on the connected socket itself before sending credentials and holds the shared lifecycle lock through registry use; the lifecycle writer takes the exclusive lock for any change to the binding or backing resources. No Docker authority, privileged helper or extra listener is required in the CLI. The paired contract §§2.1 and 2.3 specify the proposed boot-local pidfs identity and exit check, publication order and failure rules. The existing lifecycle operator uses a nonprivileged exec as the service UID in the selected container to verify the live postmaster's effective data-directory object and mount. A distinct pre-schema local SCRAM login establishes live SQL identity after socket peer verification; it is neither the bridge verifier nor the setup role. Socket and TCP proof are published together for one verified generation. The initial Linux x86-64 reference is a qualification target, not an approved support restriction; if it or an equivalent compliant mechanism cannot be qualified on the intended host, stop and seek authority before materially narrowing compatibility or expanding privileges.

### 2.3 Effective proof-role authority and fail-closed admission

Both pre-schema SCRAM proof logins—the Unix lifecycle principal in §2.2 and the private-bridge verifier in §2—may read only the live cluster identifier, designated database identity and bootstrap witness using fixed server-authorized operations. Neither can make persistent changes, including to its own password or defaults. This applies to a direct client holding the credential, not just to the normal proof caller. PostgreSQL's [self-role alteration rules](https://www.postgresql.org/docs/18/sql-alterrole.html) are not removed by HBA isolation or table grants; a utility hook alone does not cover other execution paths (see PostgreSQL 18.7 [command dispatch](https://github.com/postgres/postgres/blob/REL_18_7/src/backend/tcop/postgres.c)).

**Proposed independent control: the existing host lifecycle launcher, owned by the authorized operator of the selected local Engine.** Under the exclusive installation lock, it compares the resolved deployment to a protected release and enrollment manifest, creates a stopped DB container, inspects its exact ID and effective creation inputs, then starts only that checked ID. The approved-for-launch image identity must select one platform artifact containing the PostgreSQL executable with the guard compiled in, its loader/libraries, and the only HBA policy that admits either proof role. Launch that executable directly as the non-root postmaster, with pinned arguments and environment, from a read-only image root with no covering mounts on its executable, libraries or security files. Positive proof rules are not stored on the writable volume or supplied as an optional mount. The enrolled cluster's default HBA explicitly rejects both proof roles before any broad rule; bootstrap/recovery paths outside the guarded serving mode cannot admit them. An absent, outdated or mismatched approved manifest, image, executable selection or effective configuration stops launch before the Engine starts the server, not merely before publication. Task §2.1 specifies the closed input set and restart rules.

The guard is mandatory code, not a preload option. Bind proof enforcement to the authenticated SCRAM principal and the actual database and transport, checking before startup settings are applied and again before dispatch. For proof sessions, implement one fixed identity operation with protected object bindings, not general evaluation of client SQL. Do not let reload replace this boundary or reinterpret the checked configuration: the guarded build does not apply live security configuration changes, and the proposed mode uses only immutable configuration for its lifetime. Every managed replacement comes through the same inspection/start gate with fresh generation proof. The trust boundary is the local Engine, host administrators, and authorized operator using that gate; proof users and either CLI lack Engine, filesystem-write and signal authority over it. This is not protection against a trusted administrator deliberately running another server or overriding HBA. Preserve direct SCRAM, transports, credential separation and the existing publication and launch refusal owners. No new privileged helper, relay, listener or fallback.

**Maintenance and qualification.** Start from the PostgreSQL 18.7 source reference or a maintained equivalent. The TLSBeacon maintainer owns the versioned patch and its review against upstream changes, building against the pinned target image distribution/ABI and platform rather than copying a host-built binary. Record upstream revision/checksum, patch, compiler/build inputs and runtime dependency provenance in the release record, tied to the exact image digest and expected policy revision. Before the lifecycle operator permits any replacement baseline, requalify the affected startup, authentication, protocol, configuration, restart/reload and lifecycle evidence; a stale release must not be selected as fallback. The earlier glibc mismatch is not qualification or a supported-platform limit. Full runtime qualification is deferred to implementation (task §4, C-V01/C-V03). A compliant mechanism remains Level 1; any material authority, topology, support or risk change requires explicit Level 2 authority before dependent work.

## 3. Consequences, alternatives and authority

Compose adds Docker/Compose prerequisites and container qualification. The two CLI paths share one installation lifecycle, not two databases or two full verification stacks. The host socket adds a local filesystem access boundary and the need to qualify its owner/group, kernel process proof and managed restart behavior; unlike host TCP publication, it need not expose PostgreSQL to any additional network interface. A crash may leave the host path temporarily unavailable until the authorized lifecycle operator re-verifies the same enrolled storage and publishes a new live binding. A daemon adds privileges and lifecycle work without a D1 job to perform. No publication does not imply host-level containment of a compromised container; that hardening is outside Make automation. Fast host Go checks remain Docker-free.

Proposed layout: retain `cmd/tlsbeacon/`, the D1 domain packages and the planned `internal/registry/schema.sql`; use a root `Makefile`, `Dockerfile` and `.dockerignore`, `deployments/compose/compose.yaml`, a documented host launcher, test-only definitions under `tests/integration/`, and the planned `docs/manual-pilot.md`. Exact helper, pin and fixture ownership mechanisms are Level 1 if all invariants hold. Approved-topology changes, broader access, lost persistence guarantees and scope expansion remain Level 2; no additional Level 2 choice is identified for the protected-socket proposal as drafted. If it cannot meet these constraints, compare a compliant socket mechanism against an explicit change to DB exposure or to the two-path topology; neither broader access nor dropping host support is implicitly approved. No app/schema/config/tests or executable files are created here.

Following the independent review and explicit approval recorded above, reconcile the [architecture overview](00-architecture-overview.md) and [sole execution plan](../chunked-implementation/01-delivery-1-manual-inspection-execution-plan.md) under separate authorization, then revalidate the affected gates against committed sources and the actual environment. Historical plan/preflight or fixture reviews do not qualify product Compose or the new verification path. This draft has no execution ladder.
