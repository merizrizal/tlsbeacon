## 1. Objective and effect

On a supported Linux host with Docker Engine, Compose and Make, a trusted operator can follow the pilot guide from a clean checkout to a persistent registry and obtain a manual TLS report through the normal Compose one-off path or the supported host-run path for host-loopback-only services. Both use the same persistent enrolled registry. Full verification can be repeated on a clean checkout without using lab state or allowing a partial pass. This is an additive contract amendment, not a second delivery or ladder. It replaces the native-only pilot with two supported CLI paths over one Compose-managed PostgreSQL installation and selects Compose fixtures for the full verification path. All approved product rules, exact CLI/JSON/exits, V-01–V-10 and D2/D3 deferrals from the existing contract remain mandatory.

## 2. In-scope operating workflow

### 2.1 Pilot identity, bootstrap and recovery

- Select one explicit protected enrollment record, not Compose defaults, working directory, ambient Docker context or an arbitrary DSN. Record the local Engine identity, stable explicit Compose project, intended volume and a durable random enrollment ID witnessed on that volume, plus PostgreSQL cluster identity (for example its system identifier) and the designated database identity within that cluster. Before promoting enrollment, establish a bootstrap-owned, read-only-to-runtime deployment witness tied to the enrollment, verified cluster and database identity, independent of the D1 registry schema (for example, a restricted attestation record in a separate bootstrap-owned namespace). Capture actual cluster/database identity at bootstrap and verify it during managed lifecycle operations; a copied label or marker alone is insufficient. After schema setup, also verify the enrollment ID and compatible format in a distinct setup-owned registry marker that runtime cannot alter. A name, label, DSN or ready socket is not proof. Preserve this record with the pilot volume and configuration. A new checkout must explicitly select the same record and verified resources or fail without creating another installation.
- First bootstrap requires a deliberate first-install invocation naming the intended installation and locally selected Engine. Reserve an absent volume without adopting pre-existing resources; persist a protected pending enrollment before resource creation. Serialize concurrent lifecycle/setup operations, verify effective Compose configuration and volume mount and use fresh bootstrap inputs only for that reserved installation. Prove matching on-volume evidence and cluster/database identity before promoting enrollment to ready for `pilot-up`. If interrupted or uncertain, preserve pending evidence and storage, refuse ordinary operations and require explicit nondestructive recovery. Recovery may finish enrollment only after proving the same reserved resources and resulting cluster/database; otherwise stop and provide operator guidance without resetting, adopting or initializing anything by inference.
- Before each managed lifecycle/Compose launch operation, verify applicable Engine, volume/mount and live database/deployment identity against trusted enrollment; pin or revalidate the resources actually acted on. Before ordinary startup check the mounted volume witness and existing cluster identity nondestructively. Before launching the one-off CLI, require the independent verifier described below. The CLI independently verifies the DB peer, live cluster/database identifiers and protected deployment witness on the actual authenticated connection before any registry access, including on reconnect or connection replacement. Expose only narrowly scoped read-only identity metadata to the verifying roles; no elevated callable mutation or broad administrative membership. `pilot-init` checks schema state under setup authority; runtime schema checks belong to the CLI as in §2.2. Use no auto-initializing entrypoint in ordinary startup. Missing, mismatched, replaced, conflicting, partially initialized or incompatible state fails closed at its owning boundary; `pilot-status` may report it without claiming attachment.
- `pilot-init` runs only against the verified enrolled database with separate setup authority. Serialize init, confirm the expected pre-schema state (not merely a missing version marker), then commit all D1 schema objects, required grants and the enrolled format marker in one transaction. A compatible repeat is a no-write success; missing/inconsistent markers on unexpected existing objects are not permission to recreate. On interruption or unknown commit status, require verified read-back: complete compatible state is retained, clean pre-init state may be explicitly retried after verification, and anything partial, incompatible or unprovable requires nondestructive operator recovery. Runtime access never receives setup privileges; verify direct effective grants, including protection of immutable trust versions.
- For prelaunch proof, the host launcher runs a short-lived verifier on the private DB bridge, before starting the actual CLI. The verifier dials the exact selected live DB service on that bridge with qualified TCP server authentication, checks the live cluster and current database identifiers and reads the bootstrap-owned deployment witness on that same connection. The launcher holds the shared installation lock from protected generation selection through verifier and child registry use (hold through child termination in the normal path); managed lifecycle writers use the same lock exclusively. Pass the exact invocation's verified selection to verifier and child as protected, read-only, nonsecret launch metadata separate from runtime config. Require database TLS chain and server-name validation **and** the published generation-specific server public-key pin on every physical connection before PostgreSQL startup/authentication, with no plaintext, alternate peer, ambient override, or resumption that bypasses fresh peer proof. The child cannot replace the pin via runtime settings, and must independently match the live SQL identities/witness on that connection before registry use. `pilot-init` likewise verifies the actual setup connection using the applicable published transport binding and authenticated live proof before schema access, under its exclusive lock. No automatic pin refresh or retry of an ambiguous mutation. The lock covers cooperating lifecycle operations; if a launcher dies and loses its lock while a child survives, the child still cannot authenticate to a replacement generation. Before managed changes, prove tracked children are quiescent or stop with refusal; loss of the launcher is not proof of child termination.
- The verifier's protected connection settings and dedicated SCRAM login are provisioned with the deployment witness at bootstrap, separately from both setup and runtime configuration/credentials. Restrict that login to the designated database and the minimum read-only identity metadata; no application data access, DDL, writes, elevated memberships or callable bypass, including via PUBLIC grants. Its authenticated session must also meet the shared proof-role controls below. The verifier credential is available only to the verifier, never mounted into the child. Missing or invalid verifier proof (including its login failure) is launcher `3`, sanitized stderr only, with no CLI child.
- For each fixed child configuration or credential slot, classify only protected source-path metadata, not file contents. A confirmed absent leaf under a verified protected parent produces **no mount** for that slot; the image's fixed target is absent and has no default or fallback. A confirmed safe regular file uses an individual read-only bind with source auto-creation disabled, even if its safe mode/ownership denies the unprivileged child a read (e.g., owner-only file owned by another authorized mapped UID). The Engine must be able to mount it without widening access; neither launcher nor supervisor reads its contents, changes mode, or copies secrets to make a mount work. Protect source and parent identities against replacement through mount realization; no symlink, untrusted writer, unknown identity, broad directory mount or automatic alternate input. If the Engine cannot realize a selected safe mount (including disappearance after selection), or absence cannot be distinguished from unsafe/unavailable source infrastructure, fail as launcher `3` without running the CLI child. Do not silently reinterpret a failed bind as a confirmed missing slot. After valid selection and safe launch, the actual CLI opens/parses its inputs; confirmed missing slots, child-side permission denial, malformed inputs and rejected runtime credentials are CLI failures as below.

**Shared proof-role controls (ADR §2.3):** Apply to the bridge verifier and the Unix lifecycle role in §2.3. Authorize only fixed reads of the live cluster identifier, designated database identity and protected bootstrap witness. Use the authenticated principal and actual database and transport, not a caller-supplied identity or an application-only check. Ensure the fixed operation resolves only trusted objects and cannot invoke unintended code through name resolution or client parameters. Prevent all persistent changes, including own-password and persistent-default changes. Account for startup/session options, simple and extended SQL, utility and executor paths, callables and fast-path operations, role switching, and effective PUBLIC, default, inherited and ownership privileges. Reject or prove unavailable all channels other than the fixed identity operation and protocol handling needed for the connection.

**Independent launch gate (ADR §2.3):** The existing host lifecycle operator controls the selected local Engine and the protected expected release/enrollment records outside the checkout and data volume. At each start, under the exclusive lifecycle lock and with old publication invalidated, resolve the Compose inputs, create the DB container without starting it, then inspect that exact stopped container by immutable ID. Compare its locally realized platform image identity to the recorded digest and corresponding image/config ID; require the exact non-root user, direct PostgreSQL executable, argument vector, closed environment, read-only root, mount sources/targets/modes, private bridge, no published ports, and disabled automatic restart. Permit only named required mounts: enrolled storage, protected socket leaf, DB-only generation TLS material, the pinned auto-config input below and any explicitly qualified scratch locations. No overlay or writable path may replace the executable, loader, libraries, HBA, ident or main config. Use protected, nonreplaceable bind sources and parents through mount realization and use; forbid implicit bind creation and path indirection. Reject unknown or extra inputs. Start only that inspected ID, never a service/name selector that can recreate it. A stale, missing, invalid or mismatched manifest or realization stops before start. For reuse require evidence that the same still-live generation passed this gate; do not adopt an unknown running server. The subsequent pidfd/storage and TLS-key checks still bind publication to that live generation; they are not the admission gate.

**Closed configuration and lifecycle:** The image supplies fixed explicit main config, HBA and ident paths; pin the effective data directory and TLS paths; forbid includes, alternate paths, arbitrary command/environment overrides and unapproved native preloads. PostgreSQL also reads `postgresql.auto.conf` from the effective data directory: bind a verified empty regular file read-only at that exact path (no unverified writable effective copy) and disable `ALTER SYSTEM` in the guarded serving mode. Both positive proof rules exist only in the guarded image policy: designated roles/database, Unix `local` SCRAM for lifecycle and private-bridge TLS SCRAM for verifier, with explicit reject rules for all other database/transport combinations for both roles ahead of general rules. The cluster's default HBA and any bootstrap/recovery-only HBA reject both roles, even if their catalog credentials already exist; never start a stock server with the positive proof policy. Create/update proof principals through authorized bootstrap administration, not `pilot-up`. For first install, finish the isolated bootstrap-only stage with proof logins denied, then use the checked serving envelope for live proof before promoting pending enrollment. Leave the on-volume default config and auto-config without overrides that could defeat its proof-role rejects; verify that posture before any permitted bootstrap or recovery server start. No unchecked restart on Engine/boot or crash: disable Engine restart policy, external auto-start and PostgreSQL `restart_after_crash`; restart requires the same gate and fresh generation key. Do not support in-place reload in this managed mode. The guarded postmaster and serving backends must not apply configuration/HBA/TLS reloads on reload signals; keep those inputs immutable and disallow reload authority for ordinary SQL and OS identities. Changes require a checked replacement, not `compose up`, an unchecked `start`/`restart`, entrypoint fallback or attachment to an alternate launch. Host/Engine administrators, trusted bootstrap administration and the lifecycle operator are inside the trust boundary; deliberate overrides by them are not constrained. Neither proof users nor either CLI can control the Engine, write these inputs, signal the postmaster or start another process as the service identity.

**Guarded session:** Treat either reserved proof role as restricted regardless of which HBA rule was selected; fail if the successful SCRAM principal, designated database, actual transport or expected proof rule disagrees. Use server-owned authenticated identity and role/database catalog checks, not client-asserted parameters alone. Gate before honoring client startup options or database/role session defaults and before ready-for-query; reject unapproved startup fields and replication mode. For those sessions, recognize only the fixed identity request and the narrow protocol framing needed to return the result and close the session. Do not pass caller SQL or parameters through general parsing, planning, utility or executor paths; the server uses fixed protected catalog/object bindings and checks their expected ownership/identity before reading. Reject extended execution and fast-path messages rather than interpreting them; ordinary runtime sessions retain their own contract. No `SET ROLE`, caller-resolved functions, elevated callable operation or persistent role mutation. Inspect effective grants and defaults before and after setup. Guard admission and execution do not replace the caller's independent transport/storage check; preserve both credentials and their refusal ownership (§§2.2–2.3), with no setup/runtime fallback.

### 2.2 Scriptable launcher outcomes

- The Compose launcher refuses unsafe or unprovable deployment selection (including wrong Engine, volume, cluster or database), unavailable launch infrastructure or an unavailable schema-independent prelaunch identity check with `3` and sanitized stderr only; it does not run or impersonate the CLI. A known interruption uses `4` as below. A valid deployed DB without an application schema or with an incompatible schema must pass deployment selection and reach the CLI. After launch, the actual CLI handles runtime configuration/authentication/storage failures, a connection or identity failure discovered at runtime, and missing/incompatible/partial registry schema or marker on the enrolled DB as actionable `2` and `execution_failed` in v1 when writable. It fails before registry use, mutations or probes on these failures, never initializes or uses default policy/trust, and does not turn a failure into an empty registry. The launcher does not synthesize `2` or a CLI envelope, even if it can diagnose a problem itself.
- Run noninteractively without a TTY. Keep CLI stdout and stderr separate from launcher/Compose diagnostics; launcher diagnostics go to stderr only and are sanitized. Forward verified human stdout unchanged and verified JSON as the CLI's single `tlsbeacon.cli.v1` envelope and newline when writable; never wrap or synthesize an envelope for an infrastructure failure.
- Accept CLI exits `0`, `1` and `2` only after invocation-bound evidence of normal CLI termination and complete transfer of the streams actually produced; independently distinguish a proved child write failure from loss or truncation in capture, transport or host delivery. A feasible mechanism is a one-off in-container supervisor that waits for the actual CLI child, records normal exit versus signal and output completeness on a separate invocation-private control channel, and lets the host launcher correlate that completion with the exact container and captured bytes. A Compose exit code, stdout content or a status file from a different invocation alone is not proof. A confirmed CLI output error still maps to `2` under the original contract, even when no complete envelope is available; no partial JSON is published as a result.
- Reserve launcher exit `3` for launch/infrastructure failure (including missing or inconsistent completion proof, unexpected status and transport/output-delivery failure), and `4` for known interruption (launcher cancellation or reported signal termination before verified delivery). A launcher forcibly terminated by the OS may return a signal-derived shell status instead. Buffer or otherwise gate output until completion is verified. On launcher failure or interruption, emit no result on stdout where controllable; if interruption or sink failure occurs during final delivery, any bytes already written are unusable as a completed result. Scripts accept a result only with the documented status and, for JSON, a complete matching envelope; `2` without one is an execution failure, never a completed inspection. No inference of registry rollback or safe mutation retry follows from a missing result; use verified read-back.

### 2.3 Supported host-run path

- Install the same qualified CLI source/version and dependency baseline as the one-off image, with a recorded host artifact identity, through the pilot guide. Use a single explicitly selected, protected installation record at an absolute path (with the protected runtime connection/path settings it references); no checkout-relative, ambient DSN, socket or Docker context defaults. Keep enrollment and host socket location stable and selectable from another checkout. This is not a second setup path: only the authorized lifecycle operations can bootstrap, start or initialize the shared database.
- Use the protected PostgreSQL socket from ADR §2.2. Require trusted parent directories, validated effective ownership/mode and race-resistant reads of the actual config/secret files. Select an installation-specific socket directory under a protected parent, outside the build context, with no untrusted writers; verify the opened peer and the generation binding below before credentials, and verify the live cluster/database identifiers and bootstrap-owned deployment witness on each authenticated DB connection actually used, including replacements. Never adopt a stale socket or follow a substituted path/peer. The effective runtime identity may connect but has no authority to replace the socket, mount or protected parent. No TCP/alternate socket fallback, Docker authority, setup credentials or unrestricted DB privileges; run unprivileged. Keep credentials out of arguments, logs, build context and Git. Both CLI paths read the same registry-sourced endpoint/configuration revision, selected immutable trust version/digest and policy snapshot; local settings only bootstrap access, never shadow live registry policy or roots.
- Bind the socket to the live enrolled storage. Under the exclusive per-installation lifecycle lock, invalidate any prior protected live binding before a start, stop or replacement. The authorized lifecycle operation checks the exact Engine/container, effective data mount and on-volume evidence, and obtains a kernel process handle for that container's PostgreSQL postmaster (proposed: qualify a direct listener owned by the postmaster running as container PID 1, and obtain its host pidfd). Use the Engine's immutable container ID and live state plus the postmaster's host process and mount identity, not a name or numeric PID lookup alone: bracket acquisition with checks of its container membership and non-reused process handle, and abort on any disagreement. Verify the live database/deployment witness through the direct socket after matching its peer pidfd to that same handle, recheck the effective mount and postmaster liveness, then retain the boot ID and pidfs device/inode of the live handle with the verified enrollment/Engine/container/volume and cluster/database identities for joint publication with the TCP proof below. A raw PID, UID/GID, path or copied DB state is not generation proof. Initial source reference: upstream Linux v6.18, x86-64 with a 64-bit kernel/userspace stat ABI, pidfs `fstat` device/full inode identity and `SO_PEERPIDFD` on the connected AF_UNIX stream; match the listen-time postmaster, not its accepted backend. Pidfs assigns a boot-local 64-bit process inode from its counter on this reference; numeric PID recycling is not pidfs identity recycling. Require no inode reuse within the supported boot lifetime (no counter wrap); an option-only backport, truncated ABI, or 32-bit low inode without generation is not equivalent. Poll the retained pidfd for exit; retaining a handle does not keep the postmaster alive. Qualify these semantics on the supported lab build; this reference is not a product-wide kernel minimum or proof of support.
- **Effective storage evidence:** The lifecycle operator already controls the explicitly selected local Engine for managed operations. Use a bounded nonprivileged Engine exec by immutable container ID under the postmaster's mapped service UID/GID in the same PID/mount namespaces; no extra capability, host `/proc` inspection by the CLI, or installed privileged helper. In that context verify live PID 1 is the pinned direct PostgreSQL postmaster, open a pidfd for container PID 1 there, and compare its live full pidfs identity with that of the lifecycle operator's retained pidfd for the Engine-reported host PID. This proves the namespace-local and host handles refer to the same process without equating PID numbers; require the qualified ABI to provide the same pidfs identity from both namespaces. Open `/proc/1/cwd` in the exec context while that handle is live. The pinned PostgreSQL source changes into the effective `DataDir` after resolving configuration (including `data_directory`) and before listening. Compare that opened directory's device/inode and `statx` mount ID to the opened expected data directory from protected enrollment on the enrolled volume, and match the mount ID and mount root/target in the actual namespace mount table against the inspected Engine attachment and protected on-volume evidence. Reject alternate directories, unexpected covering mounts, external WAL/tablespaces or other registry storage outside that attachment. Do not infer this from environment or Engine metadata alone. Bracket the in-container evidence and socket proof with checks of the same still-live host handle/container and effective attachment. If the service-UID proc access, identity correlation or mount evidence cannot be qualified with existing Engine authority and effective security settings, refuse; no ptrace privilege, security-profile relaxation or fallback.
- **Pre-schema local authority:** At bootstrap provision a dedicated lifecycle-only login with a first-matching `local` HBA rule selecting only that role and designated database with `scram-sha-256`; explicitly reject that role over TCP and the bridge verifier over Unix sockets before any more general HBA rules. Do not allow a broader fallback or `trust`. Store that credential in an owner-readable-only file under the lifecycle execution identity, not the native runtime OS identity, outside child/bridge-verifier mounts. Do not pass it through arguments, environment or logs. The lifecycle operator already has Engine authority; the native runtime identity must not inherit it. After checking the exact socket peer, that operator authenticates and reads live cluster identifier, current database identity and bootstrap witness on the same connection before publication, including before app schema exists. Grant only designated DB `CONNECT`, witness namespace `USAGE` and witness `SELECT`, and access to the specific read-only cluster/database identity calls or catalog fields needed; no broad settings/catalog role, ownership, registry data access, temporary-object authority, writes or elevated callable bypass. Apply the shared server-enforced proof-role controls in §2.1 to both principals; remove unintended PUBLIC and inherited paths at bootstrap/setup. No reuse of setup or runtime credentials. Refuse publication if authentication or identity proof is unavailable or mismatched.
- **TCP binding for the same generation:** Before starting each managed postmaster generation, provision a fresh TLS keypair for that generation from the lifecycle boundary and configure only that verified DB container to load it at start, via protected read-only DB-only material outside the persistent volume (including its backups), images and child/verifier mounts. Do not reuse or reload a generation key into another process; disable unattended container/postmaster reinitialization and require managed restart and new key after crash. Keep private keys entirely out of the CLI, verifier and launch metadata. Verify the DB reads only the assigned key, then prove possession through normal validated private-bridge TLS with that public-key pin and the independent verifier's live identity proof before publication. For this initial check only, the exclusive lifecycle operator supplies the pending pin from its protected provisioning state to the verifier; pending state cannot authorize CLI or setup use. Atomically publish the nonsecret pin with the socket/process/storage binding, only while the same verified postmaster remains live. Invalidate prior publication before change, including key rotation; do not authorize replacement by a copied SQL witness, same name, same CA or old proof. Managed restart admits only the same reverified storage with a fresh binding. Out-of-band action by trusted Engine/host administrators or deliberate export of the key is outside the enforced threat model.
- The host CLI opens the stable, protected lock inode read-only and holds a shared lock from reading that binding through closing all registry connections used by the operation. It verifies the current boot, expected UID/GID and live pidfd identity on the exact connected socket before sending credentials, retains the handle through use, and verifies each new or replacement connection independently. Lifecycle operations use the same lock inode exclusively. The postmaster must not take over an inherited listener or switch backing storage while live; pin its enrolled data mount for its lifetime, disallow unverified automatic restart, and require all trusted lifecycle changes to use the managed interface. Host/Engine administrators are trusted, not adversaries the CLI can constrain. Check liveness before credentials and again before registry use; death, stale/missing binding or unprovable identity fails closed (`2`) before use of an unverified connection. The lock and liveness checks cannot prevent a crash after verification. If connection loss makes an in-flight commit ambiguous, report `commit_outcome_unknown` and require verified read-back, without fallback or blind mutation retry. A new generation is usable only after managed re-verification of the same enrolled storage. The CLI needs no access to Engine metadata or another process's private `/proc` files.
- Invoke the installed binary directly, with legacy contract §§6.1 and 7 unchanged: `0` success/healthy, `1` completed adverse inspection, `2` actionable execution failure (including unsafe selection/peer, missing or incompatible schema, and stdout failure where controllable), clean human output or single v1 envelope when writable, separate diagnostics. No launcher `3`/`4`; OS signal termination can prevent any completed result, and truncated output is not a report. Missing output/unknown commit requires verified read-back, not a blind retry.

## 3. Safety and exclusions

- Keep the pilot and each fixture run separate in effective project identity, databases, credentials, CA material, networks and volumes. Fixtures never use `.tlsbeacon-local/`, the pilot registry or arbitrary supplied databases. Validate trusted run-specific resource/dependency identity before attach or mutation through cleanup; a name, label or DSN alone is insufficient. Recheck changed resources and stop on collision or uncertainty. Any necessary fixture host port binding is loopback-only and verified; pilot ports are never published. A pilot-equivalent host socket fixture uses its own protected per-run path, never the pilot socket directory.
- Use the private database network, non-root application execution and minimal privileges as specified in the paired ADR. Protect `.tlsbeacon-local/` from Git and build-context inclusion; mount only required files read-only with effective permission checks. Setup secrets must not be available to routine CLI; sanitized diagnostics must not expose secret values. Ordinary operations must not escalate Docker, OS or database authority or modify host firewall rules.
- Only the existing configuration registry is durable in D1. No daemon, control socket, scheduler, history, current status store, alert/outbox, webhook worker, production deployment or tested backup/restore is added. Do not introduce an upgrade framework, require a second full native fixture path or bypass the approved TLS/network/trust contract for container convenience.
