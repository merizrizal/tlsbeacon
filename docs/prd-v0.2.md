## 1. Purpose and first user

TLSBeacon helps an infrastructure operator detect certificate expiry, identity mismatches, and certificate-path validation failures on explicitly configured TLS endpoints. It preserves inspection evidence and delivers actionable notifications. It observes certificates; it does not issue, renew, install, or repair them.

The first intended user is Merizrizal operating a private infrastructure lab. The pilot should answer: “Which configured endpoints need attention, what did TLSBeacon actually observe, and when?” Broader customer demand remains a hypothesis to test after the pilot.

There are two separate success criteria: the product must provide useful, trustworthy monitoring, and the engineering workflow must deliver it with proportionate planning and convergent reviews. Process metrics must not change the product's health assessments.

## 2. Product decisions

| Decision | First-release boundary | Reason |
| --- | --- | --- |
| PD-001 Operator and deployment | One trusted operator, one self-hosted Linux installation, one active monitoring service | Fits the lab pilot and bounds identity and concurrency requirements. |
| PD-002 User interface | CLI for configuration, manual inspection, status, and history; machine-readable JSON output | Supports immediate operational use and automated verification. A dashboard is later scope. |
| PD-003 Endpoint protocol | Direct TLS over TCP, initially for HTTPS-style server endpoints, with DNS names or IPv4/IPv6 addresses and an explicit port | Covers a useful subset without protocol-specific negotiation. No HTTP request is required for inspection. |

| PD-005 Notifications | One generic HTTPS webhook destination per installation | Gives a usable integration boundary without separate email, Slack, or Telegram adapters. |

## 3. User journey and scope

The operator starts TLSBeacon, configures the permitted network destinations and trust roots, and registers an endpoint. A manual inspection shows the certificate information and any validation problems. The background service repeats inspections, retains their history, and sends a webhook when a monitored condition opens, changes severity, or resolves. The operator can inspect failed notification deliveries and retry them.

The first complete MVP includes endpoint registration, manual and scheduled checks, durable history, status, inspection freshness and scheduler-state reporting, internal CA support, and durable webhook delivery. Delivery 1 is a useful manual inspection pilot; it is not yet the complete monitoring MVP. Inspection evidence and monitoring-service reliability are separate subjects: a certificate may be valid even when its scheduled monitor is overdue.

Out of scope for the MVP: certificate issuance or renewal, ACME, remediation, private-key storage, endpoint discovery or subnet scanning, public signup, multiple tenants, user-role management, a browser dashboard, STARTTLS, QUIC, authenticated client-certificate sessions, revocation checking, Certificate Transparency analysis, cipher grading, and general application availability monitoring. Approaching expiry of intermediate CA certificates is also later scope; an already-invalid chain must still fail path validation.

## 4. Functional requirements

| ID | Required product behavior |
| --- | --- |
| FR-001 Endpoint registry | Register and list stable endpoint records with a label, connection host, port, expected DNS name or IP identity, selected trust profile, check interval, and enabled state. The connection destination and expected service identity are distinct inputs, even when their textual values happen to match. Reject malformed input with an actionable error. Persist configuration across restarts. |
| FR-002 Endpoint lifecycle | Enable or disable monitoring without erasing history. Display disabled endpoints distinctly. A stable registry record may have successive monitoring identities/generations: connection target, expected identity, trust-profile selection, or effective custom-trust material changes must not reattribute old evidence to a new target or trust context. Labels, intervals, and thresholds may change with effective configuration recorded. A superseded monitoring identity and its conditions remain inspectable as historical/superseded, not actively monitored or silently recovered merely because identity changes. |
| FR-003 Manual inspection | Inspect a selected endpoint on demand. Distinguish DNS, policy-denial, connection, timeout, TLS negotiation, and certificate-validation outcomes. Report the effective contacted IP address and TLS server name (SNI, when sent) separately from the expected certificate identity. Preserve available peer-certificate evidence even when time, identity, or path validation fails; never label an unverified certificate healthy. A manual and scheduled check of the same monitoring identity must not corrupt status or create duplicate logical alerts. |
| FR-004 Certificate assessment | Report the observed leaf certificate's fingerprint, issuer, subject alternative names, validity dates, and remaining lifetime. Evaluate leaf time validity, expected identity, and certificate-path validity for server authentication independently where sufficient peer evidence exists. Preserve each supported result even when another dimension fails; explicitly mark not-assessed dimensions when a failure prevents observation or evaluation. Report the validation time used. |
| FR-005 Trust context | Associate every result with the effective trust source and a reproducible version or digest of the custom CA material used. For system roots, record the source and any reliable version identifier available; if the effective root set cannot be fingerprinted, mark its exact version unknown rather than claiming reproducible trust evidence. Replacing the contents of a same-named custom bundle cannot retroactively change an existing selected trust snapshot or old results. Importing or refreshing changed material creates a distinguishable trust generation; activation for an endpoint follows the Delivery 1 contract. A custom profile uses only its configured roots without silent system-root fallback. Do not download missing intermediates or roots automatically in the MVP. A chain-building failure must not assert an unproven cause such as “missing intermediate.” The allowance for unknown system-root provenance does not, by itself, change the approved Delivery 1 architecture’s requirement to use an enumerable, identifiable snapshot of the actual selected roots. |
| FR-006 Scheduled checks | Check enabled endpoints at their configured interval with bounded concurrency and a bounded attempt duration. Record inspection origin (manual versus scheduled) and track the latest completed scheduled attempt independently. On restart, resume monitoring and perform a current check for overdue endpoints without replaying every missed interval. Older or superseded work must not overwrite newer current status, even when it completes later. |
| FR-007 Evidence and freshness | Once durable inspection history is introduced in Delivery 2, retain immutable, timestamped completed inspections, including failed attempts, attempt source, effective destination/SNI/identity, contacted address when available, certificate details when available, configuration/trust generation, and diagnostic outcomes. Show the latest overall attempt separately from the latest certificate observation and latest scheduled completion. For persisted monitoring status, an inspection refreshes freshness only when its terminal result is durably recorded; an uncommitted attempt does not refresh persisted status. Historical success must not appear as current success after a failed or overdue check. In Delivery 1, a manual inspection may complete and produce a report without being retained by the application. Its report must not imply durable inspection history or persisted freshness. |
| FR-008 Operator output | Provide human-readable and versioned JSON status/history output. Include registry and monitoring identity, observation/validation time, evidence freshness, scheduled-monitoring state when applicable, validation results, expiry band, and actionable diagnostics. Distinguish certificate findings, probe failures, storage failures, and delayed scheduling without collapsing them into one success flag. Specify exit-code behavior in the Delivery 1 contract so scripts can distinguish execution failures from completed inspections with adverse findings. |
| FR-009 Alert lifecycle | Track expiry, identity, path-validation, reachability/negotiation, and monitoring-staleness conditions for the applicable monitoring identity. Create one logical event for an opening, severity change, or supported recovery. Repeated observations of an unchanged condition create no new event. An unavailable assessment cannot resolve an existing certificate problem; retain the previous known condition with its original evidence time, visibly distinguished from the latest failed probe. Supersession of a monitoring identity is recorded separately from evidence-based recovery; its old conditions must not remain presented as actively monitored. Manual and scheduled results must share the same event-deduplication boundary. |
| FR-010 Webhook delivery | Persist events and delivery state, send a stable event ID with each payload, retry transient failures, and expose pending, successful, and exhausted deliveries. Retries and operator replay retain the event ID and event occurrence time. Webhook delivery uses HTTPS with certificate and hostname verification, bounded attempts, destination authorization, and no automatic redirect following in the MVP. Local state must distinguish receiver acceptance from proof that a human read a notification. |
| FR-011 Recovery and disablement | Restart preserves completed history, current conditions, and pending deliveries once those capabilities are introduced. Disabling an endpoint stops new scheduled probes and new monitoring alerts; it is neither certificate recovery nor evidence that an existing condition ended. Previously created events remain visible and eligible for delivery with their original occurrence time. Re-enabling requires a fresh check and explicit reconciliation of retained conditions before any recovery or new-opening event; unchanged evidence must not produce a duplicate logical event. Unavailable fresh evidence cannot resolve a retained certificate condition. |
| FR-012 Operability | Provide startup/configuration errors, monitoring-service health, last successful persistence, scheduler lag independently from manual-inspection recency, and delivery failures. Document installation, configuration, backup and restore, and shutdown. Storage failures must not be reported as successfully persisted checks or delivered events; operators must see a degraded/unpersisted outcome instead of a fabricated successful commit. Restoration must preserve event identities in restored state; possible receiver duplicates after restore are documented. |

## 5. Interpretation of results

An observation describes one connection from the TLSBeacon host at a particular time, using one selected and authorized destination address. It does not prove that every load-balancer backend, DNS answer, network location, or end-user connection presents the same certificate. Record the contacted address when available; do not present a single-address sample as coverage of every DNS answer. A DNS name used to choose a destination, the concrete address connected, the DNS server name sent as SNI (if any), and the expected certificate DNS/IP identity serve different purposes and must not be conflated. The Delivery 1 contract defines their normalization and derivation.

Use separate result dimensions rather than allowing one “healthy” flag to hide missing evidence:

| Dimension | Meaning |
| --- | --- |
| Observation | Certificate observed, or a specific failure before sufficient evidence was available |
| Leaf time validity | Valid, not yet valid, expired, or not assessed |
| Service identity | Match, mismatch, or not assessed |
| Certification path | Pass, fail with supported diagnostic, or not assessed; includes applicable path constraints and validity checks |
| Expiry band | Normal, warning, critical, expired, or not assessed for the observed leaf |
| Inspection freshness | Current, stale, never checked, or disabled, based on the latest durably completed attempt (manual or scheduled) |
| Scheduled monitoring | On time, overdue, awaiting first scheduled result, disabled, or not applicable in the manual-only pilot; computed independently from manual inspections |

“Healthy” requires a current observation with all in-scope validation checks passing and no expiry warning. Once scheduled monitoring is active, a monitoring service that is overdue cannot display an unqualified overall “healthy” status even if a manual inspection recently passed; show the certificate finding and monitoring degradation separately. The Delivery 2 contract must define how this distinction is represented in status and versioned JSON without silently reinterpreting the Delivery 1 manual-report contract. “Healthy” means healthy under the selected checks and trust profile, not a complete security assessment. Revocation status is explicitly “not checked.”

Defaults: warning at 30 days remaining or less; critical at 7 days or less. One day means 24 hours; classification uses the actual remaining duration, not a rounded display value. Thresholds require `0 < critical < warning`. Certificate validity includes both `notBefore` and `notAfter`; an observation after `notAfter` is expired, while exactly `notAfter` is critical with zero remaining lifetime. A not-yet-valid certificate remains invalid regardless of its future expiry. Identity matching uses appropriate subject alternative names, without legacy Common Name fallback. [1][2]

A timeout produces an unavailable current assessment, even if a previous observation contained an expired certificate. Show both facts with their timestamps; the previous expiry condition stays unresolved, not reasserted as a new expiry observation. A newly observed certificate may resolve an expiry condition while an independent identity or path condition remains open. When certificates are received but one verification dimension fails, report every independently supportable dimension; when no certificate is received, do not infer validity, identity, or expiry.

Freshness rule: an enabled endpoint has stale **inspection evidence** after two configured intervals without a durably completed manual or scheduled attempt, or after two intervals since its most recent enablement if no attempt has completed in that enabled period. A recent failed recorded attempt is current evidence of failure, not healthy evidence. Independently, once scheduling is active, **scheduled monitoring** is overdue after two configured intervals without a durably completed *scheduled* attempt, measured from the most recent enablement if none has completed; a manual attempt never resets this scheduled-monitoring clock. Before Delivery 2 enables scheduling, scheduled-monitoring state is not applicable; a Delivery 1 manual report must not imply durable inspection history or persisted freshness. After re-enablement, retained results remain historical until a new check completes. The Delivery 2 contract must define time-source assumptions and exact deadline behavior.

## 6. Reliability and security boundaries

- **Target behavior:** Inspection performs DNS resolution and bounded TLS probing only. It sends no application requests, credentials, or configuration changes to monitored endpoints. A target may still record connection logs; “read-only” does not mean zero observable side effects.
- **Network authority:** Only the trusted operator may configure targets, trust profiles, or webhook destinations. Runtime probe connections and outbound webhook connections must obey operator-defined destination authorization including resolved IP addresses. Resolving or authorizing one IP must never allow a later, unchecked DNS resolution to select a different destination; connect only to a vetted address or reauthorize after any re-resolution. No anonymous network-access API. Sensitive destinations (private, loopback, link-local, and cloud-metadata ranges) require explicitly specified policy behavior, with no implicit authorization through a broad hostname allow rule. The Delivery 1 contract defines probe policy, including its safe defaults; Delivery 3 specifies the webhook egress policy.
- **Secret handling:** No monitored server private keys or client credentials are required. Protect webhook secrets, including URL/headers when they contain credentials, and redact them from reports, errors, and logs. Webhook TLS and hostname verification remain enabled even when inspected endpoints have invalid certificates; no redirect may forward credentials to another origin.
- **Evidence integrity:** Keep durably completed inspection records immutable. Bind results to the effective endpoint configuration, generation, validation time, and trust context. A persisted current-status/condition update and its logically required event must commit atomically or neither may be presented as committed. Attempts whose persistence fails cannot advance stored freshness or create an in-memory-only event masquerading as durable.
- **Notification semantics:** Durable retries provide at-least-once delivery attempts, not guaranteed delivery or exactly-once receiver processing. A receiver can deduplicate by event ID. An ambiguous response may cause the same event to be delivered twice; it must not create a second logical event. A successful HTTPS response acknowledges receiver acceptance only according to the configured integration contract, not human action.
- **Resource bounds:** Defaults are a 10-second total probe deadline and at most five concurrent probes. For the 100-endpoint target, complete one due batch within five minutes in a controlled timeout test with healthy local storage. The contract must specify the test environment and clock assumptions.
- **History:** Retention is all completed records during the pilot, with no silent automatic pruning. Document expected growth and expose storage failures. A retention policy can be a later product decision.

## 9. Product and workflow evaluation

Product acceptance requires all MVP scenarios to pass against the release candidate, plus a seven-day lab pilot using 5–10 deliberately selected endpoints. Deliberately include a private-CA target, a near-expiry or controlled-threshold case, and a reliably reachable baseline where feasible. Record incorrect assessments, inspection-staleness periods, scheduler-overdue periods, missing logical events, duplicate logical events, and receiver-level delivery duplicates separately; record deliberate fault injections apart from unexplained incidents. No known defect that misstates certificate health, loses committed events, or exceeds network authority may remain accepted as a harmless cosmetic issue. The pilot is usability and operability evidence, not proof of high availability.

Track workflow measures from the first specification review:

| Measure | Record |
| --- | --- |
| Planning effort | Elapsed time and active human time from selected scope to implementation readiness |
| Review convergence | Initial blockers, remediation rounds, reopened findings, and newly introduced blockers with their justification |
| Finding quality | Stable ID, source requirement, evidence, closure criterion, disposition, and whether future-stage evidence was incorrectly demanded |
| Decision authority | Level 0/1/2 classifications and the reason for each human escalation |
| Delivery quality | Requirement-driven rework, escaped defects, unresolved findings, and human interventions |

After two remediation rounds for the same bounded specification, inspect why convergence is failing. This is a process diagnostic trigger, not automatic acceptance and not a hard review cap. A revised workflow's success on TLSBeacon does not by itself establish improvement over LabReserve; a separately scoped historical replay would support comparison.

## 10. Next boundary

Version 0.1 approved PD-001–006 and the MVP boundary; approved v0.2 adds the clarifications in this document without expanding that boundary. The user-facing choices remain CLI-first operation, direct TLS without client credentials, and one generic webhook destination. The following technical references support certificate semantics and implementation feasibility; previously approved release boundaries and numerical defaults remain PD-001–006 and Section 5 of v0.1. The clarifications in v0.2 are approved as recorded above.

1. [RFC 5280, section 4.1.2.5](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5): certificate validity includes both endpoints of the validity interval.
2. [RFC 9525, sections 4.1 and 6](https://www.rfc-editor.org/rfc/rfc9525.html): service-identity verification uses the relevant subject alternative names; the subject Common Name is not the service-identity fallback.
3. [Go crypto/x509 Certificate.Verify](https://pkg.go.dev/crypto/x509#Certificate.Verify): path verification uses configured roots/intermediates and does not perform revocation checking. This supports keeping revocation explicitly separate from the proposed Go implementation's basic validation.
4. [Go crypto/tls Config](https://pkg.go.dev/crypto/tls#Config): default certificate verification can end a handshake before application callbacks expose peer certificates; the chosen inspection mechanism must preserve evidence without falsely treating an unverified connection as trusted.
